# AI가 코드를 짜는 시대 아키텍트가 더 중요하 이유

코딩하는 기술사 박종명님이 올리신 영상(<https://www.youtube.com/watch?v=cRViilVG6Vc)을> 메모한다.

## AI 코딩시대

코드, 테스트, 문서, 리팩토링은 AI가 더 빠르고 때로는 더 깔끔하게 만든다.
그러면 인간도 코드를 짜야할까? 어떤 코드를 어떻게, 무엇을, 얼마나 잘 해야할까?

### AI코딩 결과 == 서비스 가능?

모델하우스와 실제 건물을 예시로 보자. 모델하우스는 굉장히 깨끗하고 그럴듯해 보이지만 견본이라 눈에 보이는 부분만 신경쓰면 된다. 반면 실제 건물은 수도, 전기, 단열, 소방, 하중 등등 눈에 보이지 않는 부분까지 세밀하게 신경써야한다.  
서비스도 마찬가지이다. AI코딩으로 그럴듯하게 작동하지만 유료로 서비스할 수 있고 사고에 대하여 책임을 질수있다는 아니다.

### 실제 사례

"나는 코드를 한 줄도 쓰지 않았다." 라며 바이브 코딩만으로 서비스를 출시하는 성과를 보였다. 그러나 서비스 오픈 며칠만에 150만 API 인증 토큰 노출, 3만 5천 사용자의 이메일 주소 노출, 수천 개의 비공개 메시지 유출이 발생하는 엄청난 이슈가 발생했다. 원인은 Supabase 데이터베이스 설정 오류 및 클라이언트 측 자바스크립트에 API 키가 그대로 노출되면서 보안에 구멍이 생긴것이다. 개발자라면 API키를 그대로 노출하는 부분에서 공감을 못했을 것이다.  
그라고 AI로 작성한 코드의 45%는 보안 테스트에 실패하고 사람이 짠 코드 대비 결함 발생 비율이 1.7배 높다는 자료도 많이 있다.

### AI가 문제일까?

"AI가 코드를 짜면 위험하다"라고 생각하면 잘못된 결론이다. 진짜 결론은 "누가 품질의 경계와 기준을 **정하고**, 누가 그것을 **검증**했는가 그리고 누가 **책임**을 지는가이다"

### 서비스를 개발하며 어떤 작업을 어떻게 할것인가

계산기 기능을 만든다 하면 정답이 있기 때문에 AI가 잘한다. 그런데 우리 서비스를 MSA로 만들면 좋을까를 AI에게 질문 한다고 해보자. MSA를 단순히 소프트웨어만 보고 결정할 수 있을까?  
지금 만드는 서비스를 빠른 출시를 목표로 한다고 가정하자. 그리고 예산이 충분하지 않으며 팀 규모는 작고 역량도 주니어 위주로 있다. MSA가 무엇인지 알고 있다면 이런 환경에서 MSA를 선택하는게 쉽지 않다.
MSA뿐만 아니라 보안 수준, 성능 목표, 추후 비즈니스를 위한 확장성을 전적으로 AI에게 맡길 수 있을까? 보안 수준이 너무 높아서 성능 이슈가 발생하면? 조회 성능이 2초에서 1초로 줄이는게 맞는가? AI가 관심법으로 우리가 확장하려는 의도를 파악해서 개발할 수 있을까?  
당연히 모든 부분을 사람이 해야한다는 아니다. 판단하는데 있어 AI의 도움을 받을 수는 있지만 여러 맥락과 제한된 상황을 고려하여 **최종 결정은 사람, 아키텍트가**가 해야할 부분이 많다.

### SW 아키텍트가 하는일

아키텍트 하면 가장 먼저 떠오르는 단어는 **설계**이다. 그리고 이를 좀 더 구체적으로 정의하면 다음과 같다.

1. 정의한다: 모호한 요구를 시스템 구조, 품질, 경계 기준으로 구체화한다.
2. 제약한다: 무엇을 허용하고, 금지할것이가. 기술 스택, 보안, 코딩 컨벤션, 개발 가이드
3. 판단한다: 맥락 속에서 트레이드오프를 판단하고 중요한 설계를 결정한다. 그리고 책임진다.
4. 검증한다: 결과가 설계대로, 합의한 품질대로 만들어졌는가. 테스트를 설계하고 결과를 검증한다.

그리고 AI 시대에도 이 네 가지는 그대로 필요하다.

## 아키텍트로 설장

그렇다면 AI 시대, 어떻게 성장할 것인가

### 연주자에서 지휘자로

기존 개발자의 성장은 `특정 언어와 프레임워크를 깊이 있게 학습하고 해당 언어와 플랫폼의 전문가가 된다`라 정의할 수 있다. 연주회로 치면 특정 악기를 잘 다루는 **연주자**와 같다. 하지만 AI시대에는 AI에게 연주자 역할을 주고 여러 연주자들을 조화롭게 연주할 있도록 지휘할 수 있는 **지휘자**가 되어야 한다.

### 변하는 것과 변하지 않는것

그렇다면 좋은 지휘자가 되기 위해 어떻게 해야할까. 프론트엔드로 보면 초창기에는 순수 자바스크립트에서 시작하여 2010년 초반에는 제이쿼리, AngularJS 가 유행했지만 지금은 React, Vue, Svelte 가 유행한다. 그리고 AI 개발도구도 초반에는 커서가 유행했지만 지금은 클로드 코드, 코덱스가 유행하여 커서를 안써도 된다. 이처럼 새로운 언어, 프레임워크, 라이브러리, 툴 같은건 변한다.  
그렇다면 변하지 않는것은 무엇일까. 구조 원리, 보안 원칙, 성능, 확장성, 네트워크 등 기본은 변하지 않는다. 그래서 도구는 따라가되, 기본 원리는 파고 들어야 한다.

### 하나는 깊게, 끝까지 해봐야 한다

앞서 설명한것 처럼 AI에게 연주자 역할을 주라 했으니 개발 공부는 하지 않고  바로 지휘자 역할만 하면 된다고 생각할 수 있다. 하지만 그러면 올바른 지휘를 할 수 없다. 회사로 비유하면 우리 업무랑 아무 관련 없는 사람이 갑자기 팀장으로와서 '니들이 다 알아서 일할껀데 내가 알 필요있어?' 라고 말하는것과 같다.  
작은 것이라도 좋으니 한번은 시스템을 처음부터 끝까지 직접 만들어 보아야 한다. 그래야 구조와 동작 방식, 문제 해결의 원리를 이해할 수 있다.

### 그다음 시야를 넓혀라

시스템 개발하는데 DB 조회 시간이 30초로 시간이 너무 오래 걸리는 이슈가 발생했다고 가정하자. 실행 계획과 인덱싱을 알면 문제를 해결할 수 있지만 만약 몰랐다면 어떻게 해결해야할지 시도도 못했을 것이다. 이처럼 모르는 줄도 모르는 영역을 줄이도록 시야를 넑혀야 한다.

### 감이 아니라 기준을 배워라

회원가입, 로그인 기능을 개발하는데 보안성을 높게 개발한다고 하자. 그렇다면 과련 어떤게 보안성을 높이는 걸까? 기준을 모른다면 클로드에게 '회원가입, 로그인 기능 안전하게 만들어줘' 정도 수준일것이다. 하지만 일반적으로 많이 사용하는 기준을 안다면 '스프링 시큐리티를 사용하고 비밀번호는 SHA-256으로 암호화해' 정도 수준이 될거고 한단계 더 나아가면 'OWASP ASVS 의 인증, 개인정보 보호, 접근통제 항목 중 회원가입, 로그인 기능에 적용할 요구사항을 먼저 선정하고 항목별 구현위치, 테스트 결과, 미적용 사유를 표로 제시해' 수준까지 도달할 수 있다. 기준이 있어야 재대로 시킬 수 있고, 제대로 검증할 수 있다.

### AI 공부만 하지말고 직접 만들어라

긴말 필요없다. 백문이 불여일견이다.
