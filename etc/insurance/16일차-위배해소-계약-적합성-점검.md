# 16일차. 위배해소(계약 적합성 점검)

> 4단계 언더라이팅 연결 (인수 심사와의 접점)

## 오늘의 목표

가입 규칙 위반을 **어떻게 잡아내고 어떻게 푸는지**(위배해소) 이해한다. 설계 시스템의 사용성과 품질을 결정하는 영역이다.

## 1. 위배란?

> 설계된 계약 내용이 **가입 규칙 중 하나 이상을 충족하지 못한 상태**.

9~12일차에서 배운 모든 조건이 위배의 대상이다.

```
위배 = 규칙 검증 실패
위배해소 = 그 실패를 해결해서 정상 상태로 만드는 것
```

용어는 회사마다 다르다. **위배 / 위규 / 룰위반 / 부적합 / 에러**로 부르지만 뜻은 같다.

## 2. 위배의 종류와 심각도

모든 위배가 같은 무게를 갖지 않는다. 등급을 나눠야 한다.

| 등급 | 명칭 | 의미 | 진행 |
|---|---|---|---|
| **E (Error)** | 오류 | 절대 불가 | 설계 확정 불가 |
| **W (Warning)** | 경고 | 가능하지만 주의 | 확인 후 진행 가능 |
| **I (Info)** | 안내 | 참고 정보 | 그냥 진행 |
| **U (UW)** | 심사대상 | 설계는 되지만 심사에서 판단 | 진행, 심사 표시 |

### 예시

```
[E] 암진단비: 보험나이 70세까지 가입 가능합니다. (현재 72세)
     → 담보 제거 외에는 해소 불가

[E] 15세 미만 피보험자는 사망담보에 가입할 수 없습니다.
     → 법률 위반, 절대 불가

[W] 암진단비 가입금액이 자사 한도를 초과합니다.
     기가입 5,000만원 / 한도 7,000만원 / 신청 3,000만원
     → 2,000만원으로 조정하시겠습니까?

[U] 타사 계약이 있는 경우 심사 과정에서 가입금액이 조정될 수 있습니다.

[I] 이 담보는 10년 갱신형으로, 갱신 시 보험료가 인상될 수 있습니다.
```

**등급 분류가 곧 UX 품질이다.** 모든 걸 Error로 막으면 설계사가 일을 못 하고, 다 Warning으로 풀면 심사에서 대량 거절이 난다.

## 3. 위배해소의 방법

위배를 푸는 방법은 정해져 있다. 시스템은 **가능한 해소 방법을 제시**해야 한다.

| 위배 유형 | 해소 방법 |
|---|---|
| 연령 초과 | 담보 제거 / 다른 상품 선택 |
| 가입금액 한도 초과 | 금액 하향 조정 |
| 가입금액 배수 오류 | 가장 가까운 배수로 조정 |
| 최저 보험료 미달 | 담보 추가 / 금액 상향 |
| 부가필수 누락 | 필수 담보 자동 추가 |
| 배타 담보 동시 선택 | 둘 중 하나 제거 (선택 요구) |
| 선택그룹 미선택 | 그룹 내 하나 선택 요구 |
| 직업급수 인수불가 | 담보 제거 / 직업 재확인 |

### 자동해소 vs 수동해소

```
[자동해소 가능]
  - 부가필수 담보 자동 추가
  - 가입금액을 배수에 맞게 자동 반올림
  - 한도 초과분 자동 감액
  → 시스템이 처리하고 "이렇게 조정했습니다" 안내

[수동해소 필요]
  - 배타 담보 중 택일 → 사용자 선택 필요
  - 연령 초과 담보 → 제거할지 상품을 바꿀지 사용자 판단
  → 선택지를 제시하고 사용자에게 결정을 넘김
```

**자동해소는 편리하지만 위험하다.** 사용자 모르게 설계가 바뀌면 나중에 "내가 설계한 게 아닌데요"가 된다. 반드시 **무엇을 왜 바꿨는지 표시**해야 한다.

## 4. 위배 검증이 일어나는 시점

```
① 담보 선택/해제 시        → 즉시 (실시간)
② 가입금액 변경 시         → 즉시
③ 피보험자 정보 변경 시     → 전체 재검증
④ 설계 저장 시             → 전체 재검증
⑤ 설계서 출력 시           → 전체 재검증
⑥ 청약 전환 시             → 전체 재검증 (필수)
⑦ 심사 결과 반영 후        → 전체 재검증 (필수)
```

### 실시간 검증과 전체 검증을 둘 다 해야 하는 이유

실시간 검증은 **방금 바뀐 것 주변만** 본다. 성능 때문이다. 그런데 이런 상황이 생긴다.

```
1. 담보 A, B 선택 (정상)
2. 피보험자 생년월일 수정 → 보험나이 71세로 변경
3. A는 70세까지만 가능 → 위배 발생
   하지만 "생년월일 변경"이 A의 검증을 트리거하지 않았다면? → 통과되어 버림
```

그래서 **저장·출력·전환 시점에 전량 재검증**하는 안전망이 반드시 필요하다.

## 5. 좋은 위배 메시지의 조건

이게 실무 품질을 가른다.

### 나쁜 예

```
❌ 가입할 수 없습니다.
❌ 오류가 발생했습니다. (ERR-4021)
❌ 조건에 맞지 않습니다.
```

### 좋은 예

```
✅ 암진단비는 보험나이 70세까지 가입 가능합니다.
   현재 피보험자 보험나이는 72세입니다.
   [담보 제거] [다른 상품 보기]

✅ 암진단비 가입금액이 자사 한도를 초과했습니다.
   • 기가입 금액 : 5,000만원 (계약 2건)
   • 자사 한도   : 7,000만원
   • 신청 가능액 : 2,000만원
   [2,000만원으로 조정] [기가입 계약 보기]
```

좋은 메시지의 4요소:

1. **무엇이** 문제인가 (담보명 명시)
2. **왜** 문제인가 (기준값)
3. **현재** 값은 얼마인가 (실제값)
4. **어떻게** 해결하나 (액션 버튼)

## 6. 시스템 관점

### 검증 결과 구조

```json
{
  "설계번호": "D20260923001",
  "검증결과": "NG",
  "확정가능여부": false,
  "위배목록": [
    {
      "위배코드": "AGE_OVER",
      "등급": "E",
      "담보코드": "C001",
      "담보명": "암진단비",
      "메시지": "암진단비는 보험나이 70세까지 가입 가능합니다.",
      "기준값": 70,
      "실제값": 72,
      "해소방법": [
        {"유형": "REMOVE_COVERAGE", "라벨": "담보 제거"},
        {"유형": "CHANGE_PRODUCT", "라벨": "다른 상품 보기"}
      ]
    }
  ]
}
```

핵심 원칙:

1. **위배는 목록으로 반환한다.** 첫 번째 위배에서 멈추면 사용자가 고칠 때마다 새 위배를 만난다. 한 번에 다 보여줘야 한다.
2. **기준값과 실제값을 항상 담는다.** 메시지를 클라이언트에서 조립할 수도 있어야 한다.
3. **해소방법을 서버가 제시한다.** 비즈니스 규칙이므로 화면이 판단하면 안 된다.
4. **등급으로 진행 가능 여부를 결정한다.** `확정가능여부 = 위배목록에 E가 없음`.

### 성능 설계

설계 화면은 조작할 때마다 검증이 돈다. 담보 100개, 규칙 500개면 무거워진다.

- **증분 검증 + 전량 검증 분리**: 평소엔 영향 범위만, 확정 시엔 전량
- **룰 캐싱**: 상품별 규칙 세트를 메모리에 올려둔다
- **검증 순서 최적화**: 9일차의 검증 순서대로, 앞에서 걸리면 뒤는 스킵

### 위배 이력 관리

```
설계위배이력
  설계번호, 검증일시, 위배코드, 등급, 해소여부, 해소방법
```

왜 필요한가:

- **어떤 규칙에서 설계사들이 자주 막히는지** 분석 가능 → 상품·UX 개선 자료
- 심사 단계에서 "설계 때 이런 경고가 있었다"는 맥락 제공
- 분쟁 시 증빙

## 7. 위배해소와 언더라이팅의 관계

```
설계 단계 위배      → 시스템이 잡는다 → 설계사가 해소
심사 단계 부적합    → 언더라이터가 잡는다 → 조건부 인수로 해소 (15일차)
```

두 단계는 **같은 구조**를 가진다.

| | 설계 위배 | 심사 부적합 |
|---|---|---|
| 검출 | 룰 엔진 | 룰 엔진 + 사람 |
| 해소 | 담보/금액 조정 | 할증/부담보/감액 |
| 결과 | 설계 확정 | 계약 성립 |
| 거부 시 | 설계 포기 | 청약 철회 |

설계 단계에서 잘 거를수록 심사 부하가 줄고, 고객 경험이 좋아진다. **위배해소 기능의 품질 = 회사의 자동인수율**로 이어진다.

## 오늘의 정리

- 위배 = 가입 규칙 검증 실패, 위배해소 = 이를 해결하는 과정
- 위배는 **등급(E/W/I/U)** 으로 나눠야 한다. 다 막아도, 다 풀어도 안 된다
- 자동해소는 편리하지만 **무엇을 왜 바꿨는지 반드시 표시**해야 한다
- 실시간 검증 + **저장/출력/전환 시점 전량 재검증**이 안전망
- 좋은 메시지는 무엇·왜·현재값·해결방법 4요소를 담는다
- 위배는 **목록으로** 반환하고, 해소방법은 서버가 제시한다
- 설계 위배해소와 심사 조건부 인수는 같은 구조의 다른 단계다
