# 17일차. 상품 구조와 상품코드 체계

> 5단계 상품과 프로세스 (전체 그림)

## 오늘의 목표

**상품 - 플랜 - 담보**가 코드 체계로 어떻게 묶이는지 이해하고, 상품 개정과 판매 기간 관리가 왜 중요한지 파악한다.

## 1. '상품'이란 무엇인가

지금까지 배운 것들을 묶는 상위 개념이다.

```
상품 (Product)
 └─ 플랜 (Plan)          ── 정형화된 담보 조합
     └─ 담보 (Coverage)  ── 실제 보장 단위
         └─ 요율 (Rate)  ── 보험료 계산 기준
```

### 상품이 담고 있는 것

| 항목 | 예시 |
|---|---|
| 상품명 | 무배당 건강한종합보험 2601 |
| 상품 유형 | 장기인보험 / 손해보험 |
| 판매 채널 | 대면 / TM / CM / GA |
| 판매 기간 | 2026-01-01 ~ 2026-12-31 |
| 가입 가능 연령 | 만 15세 ~ 70세 |
| 주계약 | 상해사망후유장해 |
| 부가 가능 특약 | 150개 |
| 적용 규칙 세트 | 담보관계, 한도, 직업 규칙 |

**상품은 "판매 가능한 조합의 집합을 정의한 것"** 이라고 보면 된다.

## 2. 상품코드 체계

### 코드에 담기는 정보

회사마다 다르지만, 일반적으로 이런 정보가 들어간다.

```
  A  L  01  2601  01
  │  │  │   │     └─ 개정 차수
  │  │  │   └─────── 출시 연월 (2026년 1월)
  │  │  └─────────── 상품 일련번호
  │  └────────────── 상품 계열 (L=장기, G=일반, A=자동차)
  └───────────────── 회사/사업부 구분
```

### 왜 코드에 버전이 들어가나 — 가장 중요한 부분

보험 상품은 **개정**된다. 요율이 바뀌고, 담보가 추가되고, 약관이 수정된다.

그런데 **기존 계약은 가입 당시 조건대로 유지되어야 한다.**

```
2026-01  AL0126 01 판매 시작
2026-07  요율 개정 → AL0126 02 로 판매
2027-01  담보 추가 → AL0127 01 로 판매

2026-03 가입 고객 → 평생 AL0126 01 기준으로 관리
2026-09 가입 고객 → 평생 AL0126 02 기준으로 관리
```

즉 **상품은 시간이 지나도 사라지지 않는다.** 판매는 중지되지만 계약 관리를 위해 영원히 살아 있어야 한다.

이것이 보험 시스템이 다른 도메인보다 복잡한 핵심 이유 중 하나다. **모든 마스터 데이터에 버전과 유효기간이 붙는다.**

## 3. 플랜(설계안)

**플랜**은 자주 쓰이는 **담보 조합을 미리 묶어둔 것**이다.

```
[실속플랜]
  암진단비 2,000만원
  뇌혈관진단비 1,000만원
  허혈성심장질환 1,000만원
  → 월 26,000원

[표준플랜]
  암진단비 3,000만원
  뇌혈관진단비 2,000만원
  허혈성심장질환 2,000만원
  질병입원일당 3만원
  질병수술비 30만원
  → 월 46,000원

[고급플랜]
  ... → 월 82,000원
```

### 플랜의 역할

1. **설계 속도**: 담보 150개 중에서 고르는 대신 클릭 한 번
2. **품질 보장**: 회사가 검증한 조합이므로 위배가 없다
3. **비교 제시**: 고객에게 3가지 안을 나란히 보여주기 쉽다
4. **불완전판매 방지**: 검증된 조합이므로 설명 누락 위험이 적다

18일차에서 자세히 다룬다.

## 4. 상품 - 플랜 - 담보의 연결 구조

```
상품 (PRODUCT)
  상품코드, 상품명, 상품유형, 판매시작일, 판매종료일, 채널구분
      │
      ├── 상품담보 (PRODUCT_COVERAGE)         ── 이 상품에 붙일 수 있는 담보 목록
      │     상품코드, 담보코드, 주계약여부,
      │     필수여부, 정렬순서,
      │     최소가입금액, 최대가입금액, 가입금액단위,
      │     가입가능최소연령, 가입가능최대연령,
      │     납입기간목록, 보험기간목록,
      │     갱신여부, 갱신주기
      │
      ├── 담보관계규칙 (COVERAGE_RELATION)     ── 10일차
      ├── 담보선택그룹 (COVERAGE_GROUP)        ── 10일차
      ├── 한도기준 (LIMIT_RULE)               ── 11일차
      ├── 직업규칙 (COVERAGE_JOB_RULE)         ── 12일차
      │
      └── 플랜 (PLAN)
            상품코드, 플랜코드, 플랜명, 정렬순서
                └── 플랜담보 (PLAN_COVERAGE)
                      상품코드, 플랜코드, 담보코드,
                      기본가입금액, 변경가능여부, 제외가능여부
```

### 중요한 설계 포인트

**담보 마스터는 상품과 분리한다.**

```
담보마스터 (COVERAGE_MASTER)    ── 담보의 본질적 정의 (전사 공통)
  담보코드, 담보명, 담보유형, 지급방식, 약관조문

상품담보 (PRODUCT_COVERAGE)     ── 이 상품에서 이 담보를 어떻게 쓰는가
  상품코드, 담보코드, 최소/최대금액, 가입연령...
```

같은 "암진단비" 담보가 A상품에서는 최대 3,000만원, B상품에서는 5,000만원일 수 있다. **담보의 정의는 하나, 상품별 적용 조건은 여러 개**다. 이 분리를 안 하면 담보가 상품 수만큼 복제되어 관리가 불가능해진다.

## 5. 판매 기간과 상품 상태

```
[개발중] → [승인대기] → [판매예정] → [판매중] → [판매중지] → [관리중]
                                          ↓
                                      [일시중지]
```

| 상태 | 신규 설계 | 기존 계약 관리 | 갱신 |
|---|---|---|---|
| 판매중 | 가능 | 가능 | 가능 |
| 일시중지 | 불가 | 가능 | 가능 |
| 판매중지 | 불가 | 가능 | 가능(상품별 정책) |
| 관리중 | 불가 | 가능 | 정책에 따름 |

**"판매중지된 상품도 시스템에서 지워지지 않는다."** 20년, 30년 전 상품의 계약이 아직 살아 있기 때문이다. 오래된 보험사 시스템에 상품 코드가 수천 개씩 쌓여 있는 이유다.

## 6. 상품 개정 시 고려사항

상품을 고칠 때 무엇이 바뀌는가에 따라 처리가 다르다.

| 변경 내용 | 처리 |
|---|---|
| 요율 변경 | 새 요율 버전 등록, 적용일 기준 분기 |
| 담보 추가 | 상품담보 행 추가 (기존 계약 무영향) |
| 담보 삭제 | 신규 가입만 막고, 기존 계약은 유지 |
| 한도 변경 | 새 한도 버전, 적용일 기준 |
| 약관 변경 | **새 상품 코드로 분리**하는 것이 원칙 |

**약관이 바뀌면 다른 상품이다.** 보장 내용이 달라지므로 같은 코드로 관리하면 나중에 "이 계약의 약관이 무엇이냐"를 특정할 수 없다.

## 7. 시스템 관점 — 실무 함정

1. **모든 마스터에 적용기간 컬럼을 넣어라.** `적용시작일`, `적용종료일`. 안 넣고 시작하면 나중에 넣을 수 없다.

2. **조회는 항상 기준일과 함께.**
   ```sql
   WHERE 상품코드 = ?
     AND 적용시작일 <= :기준일
     AND (적용종료일 IS NULL OR 적용종료일 >= :기준일)
   ```
   기준일은 설계일 / 청약일 / 계약일 / 갱신일 중 무엇인지 명확히 정의해야 한다.

3. **계약에는 스냅샷을 남겨라.** 마스터가 바뀌어도 계약 내용이 흔들리지 않도록 상품코드, 요율버전, 약관버전을 계약에 박아둔다.

4. **상품 등록 화면(상품 팩토리)이 별도 시스템이다.** 상품 하나 만드는 데 담보 150개 × 조건 수십 개를 등록해야 한다. 개발자가 SQL로 넣는 방식으로는 운영이 불가능하다. **상품 관리 도구**가 반드시 필요하고, 실제로 보험 IT에서 가장 중요한 시스템 중 하나다.

5. **상품 복제 기능.** 신상품 대부분은 기존 상품의 변형이다. "복제 후 수정"이 되어야 한다.

## 오늘의 정리

- 상품은 **판매 가능한 담보 조합과 규칙의 집합**을 정의한 것
- 상품코드에는 **버전(개정 차수)** 이 포함되고, 상품은 판매가 끝나도 영원히 관리된다
- **담보 마스터(본질)** 와 **상품담보(상품별 적용 조건)** 를 분리해야 한다
- 플랜은 검증된 담보 조합 묶음으로, 설계 속도와 품질을 동시에 잡는다
- 모든 마스터에 **적용기간**이 붙고, 조회는 **기준일**과 함께 한다
- 계약에는 사용된 버전을 **스냅샷**으로 남긴다
- 상품 등록 도구는 보험 IT의 핵심 시스템이다
