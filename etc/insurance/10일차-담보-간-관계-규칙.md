# 10일차. 담보 간 관계 규칙 — 부가필수 / 부가가능 / 배타 / 선택그룹

> 3단계 가입조건과 규칙 (가입설계의 핵심)

## 오늘의 목표

1일차에서 예고한 **담보 조합 규칙**을 제대로 배운다. 가입설계 시스템의 가장 복잡하고 가장 자주 버그가 나는 영역이다.

## 1. 왜 담보를 마음대로 조합할 수 없나

세 가지 이유가 있다.

### ① 상품 설계의 논리적 일관성

"암수술비"를 넣으면서 "암진단비"를 안 넣는 것은 상품 논리상 이상하다. 수술의 전제가 진단이기 때문이다.

### ② 역선택 방지

고위험 담보만 골라 담는 것을 막아야 한다. 위험한 담보만 쏙쏙 뽑아 가입하면 손해율이 터진다.

### ③ 중복 보장 방지

"암진단비(유사암포함)"와 "유사암진단비"를 같이 넣으면 유사암이 이중 지급된다. 이런 조합은 막아야 한다.

## 2. 네 가지 핵심 규칙

### ① 부가필수 (필수부가)

> A를 가입하면 **B도 반드시 가입해야 한다.**

```
암진단비 선택 → 유사암진단비 자동 포함
주계약 → 무조건 포함 (모든 계약의 부가필수)
```

**시스템 동작**: A 선택 시 B를 **자동으로 추가**하고, B 단독 해제를 막는다. 사용자가 B를 지우려 하면 "암진단비 가입 시 필수 담보입니다"라고 안내한다.

### ② 부가가능 (선행조건, 종속)

> B를 가입하려면 **A가 먼저 있어야 한다.** 단, A만 있어도 된다.

```
암수술비  ← 암진단비가 있어야 가입 가능
암입원일당 ← 암진단비가 있어야 가입 가능
```

**부가필수와의 차이**가 핵심이다.

| | 부가필수 | 부가가능 |
|---|---|---|
| A 선택 시 | B가 자동으로 따라온다 | B는 선택 가능해질 뿐 |
| A 없이 B만 | 불가 | 불가 |
| A만 단독 | 불가 (B가 따라오므로) | 가능 |

**시스템 동작**: A가 없으면 B를 비활성(disabled) 처리한다. A를 해제하면 B도 함께 해제되어야 한다.

### ③ 배타 (상호배제)

> A와 B는 **동시에 가입할 수 없다.**

```
암진단비(유사암포함)  ⇔  유사암진단비        (중복 보장)
실손의료비(신규)      ⇔  실손의료비(전환)     (하나만)
간병인사용일당       ⇔  간병인지원일당       (택1)
```

**시스템 동작**: A 선택 시 B를 비활성화하거나, B가 이미 선택되어 있으면 "함께 가입할 수 없습니다. 어떤 것을 유지하시겠습니까?"를 묻는다.

### ④ 선택그룹 (택일)

> 그룹 안에서 **정해진 개수만** 선택할 수 있다.

```
[입원일당 그룹] 중 1개만 선택
  ├─ 질병입원일당(1일이상)
  ├─ 질병입원일당(3일초과)
  └─ 질병입원일당(종합병원)

[플랜 그룹] 중 1개 필수 선택
  ├─ 실속형
  ├─ 표준형
  └─ 고급형
```

**시스템 동작**: 라디오 버튼처럼 동작한다. 최소/최대 선택 개수를 룰로 관리한다(1개만, 최대 3개, 최소 1개 등).

## 3. 규칙이 겹칠 때

실제 상품에서는 이 규칙들이 **동시에, 그리고 연쇄적으로** 걸린다.

```
암진단비(유사암제외)
  ├─ [부가필수] 유사암진단비
  ├─ [부가가능] 암수술비
  ├─ [부가가능] 암입원일당
  │                └─ [배타] 암입원일당(요양병원)
  └─ [배타]     암진단비(유사암포함)
```

여기서 생기는 실무 문제들:

### 연쇄 해제 (Cascade)

암진단비를 해제하면?

```
암진단비 해제
  → 유사암진단비 자동 해제 (부가필수였으므로)
  → 암수술비 자동 해제 (부가가능 선행조건 소멸)
  → 암입원일당 자동 해제
  → 암입원일당(요양병원)도 해제
```

**한 번의 클릭이 5개 담보를 지운다.** 사용자에게 반드시 사전 고지해야 한다. "암진단비를 제외하면 관련 담보 4건이 함께 제외됩니다. 계속하시겠습니까?"

### 순환 참조

A가 B를 필수로 하고, B가 A를 필수로 하는 경우. 논리적으로는 가능하지만 구현 시 **무한 루프**가 된다. 룰 등록 시점에 순환을 검출해야 한다.

### 규칙 충돌

부가필수로 B를 넣어야 하는데, 이미 선택된 C와 B가 배타 관계라면? 이런 충돌은 **룰 등록 시 검증**해서 막거나, 런타임에 우선순위를 정해 처리해야 한다.

## 4. 규칙의 적용 시점

| 시점 | 처리 |
|---|---|
| 담보 선택 시 | 즉시 검증, 자동 추가/제거 |
| 가입금액 변경 시 | 연동 담보의 금액 제약 재검증 |
| 설계 확정 시 | 전체 규칙 일괄 재검증 (최종 안전망) |
| 청약 전환 시 | 다시 한번 전체 검증 |

**설계 확정 시 전체 재검증이 반드시 필요하다.** 화면에서 실시간 검증을 하더라도, 순서에 따라 빠져나가는 케이스가 반드시 생긴다. 마지막에 전량 검사하는 안전망을 둬야 한다.

## 5. 시스템 관점

```
담보관계규칙 (COVERAGE_RELATION)
  상품코드,
  기준담보코드,        ── A
  대상담보코드,        ── B
  관계유형코드,        ── MUST(부가필수) / CAN(부가가능) / EXCL(배타)
  적용시작일, 적용종료일,
  메시지코드

담보선택그룹 (COVERAGE_GROUP)
  상품코드, 그룹코드, 그룹명,
  최소선택수, 최대선택수

담보선택그룹상세
  상품코드, 그룹코드, 담보코드, 정렬순서
```

### 구현 전략

1. **규칙 엔진으로 분리한다.** 화면 로직에 섞지 말 것. 화면(웹), 설계API, 청약, 배치가 모두 같은 규칙을 써야 하므로 **공통 모듈**이어야 한다.

2. **선언적 데이터로 관리.** 상품 하나 추가될 때마다 if문이 늘어나면 유지보수가 불가능해진다.

3. **그래프 탐색으로 연쇄 처리.** 담보 관계는 방향 그래프다. 추가 시에는 정방향 탐색(필수 담보 수집), 제거 시에는 역방향 탐색(나에게 의존하는 담보 수집)을 한다.

4. **결과에 이유를 담는다.**
   ```json
   {
     "action": "AUTO_ADD",
     "coverage": "유사암진단비",
     "reason": "암진단비의 필수부가 담보",
     "triggeredBy": "암진단비"
   }
   ```
   UI가 "왜 이게 추가됐는지"를 설명할 수 있어야 한다.

5. **테스트 케이스를 규칙 데이터로부터 생성한다.** 조합의 수가 폭발적이므로 수동 테스트로는 커버가 안 된다.

## 오늘의 정리

- 담보 조합은 자유롭지 않다. 논리 일관성·역선택 방지·중복 방지 때문이다
- **부가필수**: A 넣으면 B 자동 포함 / **부가가능**: A 있어야 B 선택 가능
- **배타**: A와 B 동시 불가 / **선택그룹**: 그룹 내 N개 택일
- 규칙은 연쇄된다 → 담보 하나 제거가 여러 담보를 연쇄 제거할 수 있다
- 규칙은 **데이터로 관리하고 공통 규칙 엔진으로 처리**한다
- 설계 확정 시 전체 재검증 안전망이 반드시 필요하다

## 스스로 확인하기

1. 부가필수와 부가가능의 차이를 한 문장으로 설명해보자.
2. "암진단비(유사암포함)"과 "유사암진단비"가 배타인 이유는?
3. 담보 A를 해제할 때 시스템이 해야 할 일을 순서대로 나열해보자.
