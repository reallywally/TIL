# EAI는 왜 필요할까

메가웨어라는 EAI 솔루션을 처음 만났다. API 게이트웨이와 비슷한 역할을 한다고 들었는데, 막상 레이아웃 문서를 보니 요청/응답이 중간에서 형태가 바뀐다. 그리고 단순 REST API만 개발해서 그런지 그냥 요청하고 응답 받으면되지 중간에 이런 시스템이 있는게 꽤 낯설었다. 그리고 왜 필요한지 이해하는 과정을 정리해 본다. 대부분은 클로드를 참고하여 작성하였다.

## 1. EAI가 뭔데?

- 주로 공공·금융권에서 기간계(핵심 업무 시스템)와 외부 시스템을 연결하는 데 쓰인다.
- 보험사에서는 **FEP(Front End Processor)** 역할로 쓰인다. 대외기관(보험개발원, 금융결제원, 은행, 카드사 등)과 주고받는 전문을 모두 이 녀석이 거친다.

> **용어 정리**
>
> - **기간계**: 보험 계약·보상 같은 핵심 업무를 처리하는 내부 시스템
> - **대외기관**: 우리 회사 밖에 있는 상대 시스템
> - **전문(電文)**: 시스템끼리 주고받는 메시지. JSON이 아니라 **고정길이 문자열**인 경우가 많다.
> - **FEP**: 대외기관과의 통신을 전담하는 중계 서버

## 2. 처음 든 의문: "게이트웨이면 그냥 통과시키면 되는 거 아니야?"

내가 알던 API 게이트웨이는 이렇다.

```text
A 서버 → [Gateway: 인증, 라우팅, 로깅] → B 서버
```

이처럼 일반적인 API 였다면 바디는 손대지 않고 그대로 넘긴다. 그런데 EAI(FEP 레이아웃 문서)는 요청 하나에 **구간이 4개**로 나뉘어 있었다.

| 번호 | 방향 | 설명 |
| --- | --- | --- |
| ① | 기간계 → FEP | 기간계 표준 헤더 + payload |
| ② | FEP → 대외기관 | **기관이 실제로 받는** 전문 구조 |
| ③ | 대외기관 → FEP | 기관이 보내는 응답 전문 |
| ④ | FEP → 기간계 | 다시 표준 헤더로 감싼 응답 |

①과 ②가 다르게 생겼고, ③과 ④도 다르다. "왜 중간에서 바꾸지?"가 첫 번째 질문이었다.

## 3. 답: FEP는 게이트웨이가 아니라 **통역사**다

핵심은 이거였다. **상대방이 우리와 같은 언어를 쓰지 않는다.**

대외기관은 기관마다 전문 규격이 전부 다르다. 고정길이 전문, 기관별 헤더, 인코딩, TCP 소켓, 파일 배치, 가끔 SOAP까지. 우리가 "JSON으로 주세요"라고 요구할 수 없을 수도 있다.

그렇다고 기간계가 기관 30곳의 규격을 전부 알고 있으면, 기관 하나가 스펙을 바꿀 때마다 기간계를 고쳐서 재배포해야 한다. 그래서 **번역을 FEP 한 곳에 몰아넣은 것**이다.

### 봉투(Envelope) 패턴으로 이해하기

```text
① 기간계 → FEP
{
  표준헤더: { 거래ID, 송신시스템, 기관코드, ... },   ← 봉투
  payload: { 기관헤더, 기관바디 }                     ← 편지
}

② FEP → 기관
  봉투를 뜯고, 편지를 기관 규격(고정길이 전문 등)으로 다시 포장해서 전달

③ 기관 → FEP
  기관 규격 그대로 응답 수신

④ FEP → 기간계
  다시 표준헤더 봉투에 넣어서 반환
```

기간계 개발자는 **표준 헤더 + payload** 구조 하나만 알면 된다. payload 내용은 기관별 레이아웃 엑셀을 보고 채우면 끝.

### API 세계의 비슷한 개념

- **Adapter / Anti-Corruption Layer**: 외부 시스템의 규격이 내부 도메인으로 새어 들어오지 않게 경계에서 변환

## 4. 추가 의문: "③에 없던 필드가 ④에 생기면 이상한 거 아니야?"

원칙은 맞다. **업무 데이터는 기관이 안 준 걸 FEP가 지어낼 수 없다.** payload 안의 값이 ③에 없는데 ④에 있으면 그건 이상한 게 맞다.

다만 ④에 ③에 없던 필드가 **정상적으로** 생기는 경우가 있다.

| 유형 | 예시 | 출처 |
| --- | --- | --- |
| 표준 헤더 필드 | 거래ID, 전문 길이, 처리일시, 응답코드 | FEP가 생성 |
| 요청 정보 echo | ①에서 받은 송신시스템 ID, 요청 키 | ① |
| FEP 상태값 | 기관 타임아웃, 통신 오류, 전문 형식 오류 코드 | FEP가 생성 |
| 변환·파생값 | 기관 결과코드 `A1` → 사내 표준코드 `9001`, 날짜 포맷 변환 | ③ (이름/값만 바뀜) |
| 상수/기본값 | 기관이 안 주는 필수 항목을 빈값·고정값으로 채움 | 매핑 정의 |

## 5. 결론

1. **FEP는 게이트웨이가 아니라 통역사다.** 중간에서 형태가 바뀌는 건 버그가 아니라 존재 이유.
2. 기간계는 **표준 헤더 + payload** 하나만 알면 된다. 기관별 규격은 FEP가 흡수한다.

## 6. 기타 테스트

호기심에 몇가지 테스트한 내용도 추가해본다.

- 요청, 응답시 전문 등록에 없었던 필드를 추가하면 실제 주고 받을 때도 없다.
- 에러 메시지가 서버에서 발생한건지 EAI 시스템에서 발생한건지 잘 확인해야 한다.
- 메가웨어라는 솔루션 기준 왼쪽 상단 관리 메뉴에서 등록된 인터페이스 목록과 상세 정보를 확인 할 수 있다.
