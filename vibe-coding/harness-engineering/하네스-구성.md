# 하네스 구성

## 3가지 핵심 구성 요소

핵심 구성 요소는 에이전트, 스킬, 오케스트레이터이다. 각각에 대하여 다음과 같이 정리할 수 있다.

| 구분 | 에이전트 | 스킬 | 오케스트레이터 |
| --- | --- | --- | --- |
| 개념 | 누가 이 작업을 하는가 | 이 작업을 어떤 절차로 하는가 | 누가 언제 누구와 무엇을 할것인가 |
| 정의하는것 | 역할 설정, 판단 기준, 협업 규칙 | 워크플로, 트리거, 절차지식 | 팀 구성, 작업 의존성, phase 전환 |
| 파일 위치 | .claude/agents.{name}.md | .claude/skills/{name}.md | 세션 런타임 + CLAUDE.md |
| 영속 단위 | 역할 | 절차 | 실행 흐름 |
| 트리거 | 에이전트 도구로 명시 호출 | description 매칭으로 자동로드 | 사용자 요청, 단계 전환 |
| 부재시 생기는 문제 | 역할 표류, 매 세션 재정의 | 매번 절차 재발명, 결과 편차 | 리더 병목, 순차 퇴행 |

## 3가지 핵심 요소가 섞이면 생기는 문제

### 안티패턴 1. 에이전트 한 명이 모든 역할을 다 맡는다

- 상황: super-dev.md 같은 에이전트 하나에 기획, 코딩, 리뷰, 배포 모두 다 하는 역할이 있음
- 문제점:
  - 처음 놓친 문제를 다시 놓친다.
  - 코딩만 필요한 상황에서도 기획, 리뷰, 배포 원칙을 지켜야 하여 재사용이 막힌다.
  - 많은 역할이 있어 수정하기가 어렵다.
- 해결 방법:
  - 역할을 쪼개어 3~4인 에이전트로 분리한다.
  - 여러 에이전트가 공통으로 쓰는 절차가 있다면 스킬로 분리한다.

### 안티패턴 2. 스킬이 팀 전체를 지휘하려 한다

- 상황: 스킬 본문에 "조건 A면 에이전트 X를 부르고, 조건 B이면 Y를 부르고, Y가 실패하면 Z를 3회 재시도하고 ..."가 20단계를 넘어간다.
- 문제점:
  - 스킬은 함수처럼 '어떻게 하는가'에 집중해야한다.
  - 단계 전환, 에러 복구 등 모든 기능을 처리하려하면 스킬 본연의 정체성을 읽게 된다.
- 해결방법:
  - 단순 순서라면 상관없고 팀이 커지고 분기가 복잡해지면 도구로 분리한다.
- 예외:
  - 스킬의 주어가 "절차"라면 분기는 가볍게 두고 조율은 밖으로 뺀다.
  - 스킬의 주어가 "팀 조율"이라면 phase를 직접 선언해도 된다.

### 안티패턴 3. 리더가 직접 일을 처리한다

- 상황: 리더 에이전트가 팀원 에이전트에게 일을 시키지 않고 직접 diff를 읽고, 직접 리뷰를 쓰고, 직접 수정한다.
- 문제점:
  - 팀원이 네명이나 있어도 모든 정보가 리더를 거쳐야 한다면 팀원은 서로이 존재를 모른 채 각자의 방에 갇혀있는것과 같다.
- 해결방법:
  - 오케스트레이터는 설계자 역할만 한다.
  - 리더는 중개하지 않는다.

### 안티패턴 4. 에이전트 파일에 절차 지식을 다 넣는다

- 상황: 에이전트 정의 파일이 500줄이 넘는다.
- 문제점:
  - 여러 에이전트가 공유해서 사용하는 내용이 에이전트 파일마다 작성하면 다중관리가 돤다.
  - 다중관라거 되어 1개를 수정하면 전체를 수정해야하고 실수로 수정을 안하면 판정 기준이 달라진다.
- 해결방법:
  - 공통 지식을 스킬을로 분리한다.
