# 샵 밸류(SHAP Value)가 무엇인고

샵 밸류를 직접 코딩할 필요는 없지만 커뮤니케이션하는데 필하여 클로드에게 정리하라고 시켰다.

## 1. 문제 상황부터

모델을 하나 만들었다고 하자. 고객 정보를 넣으면 인수 거절 확률 0.87을 뱉는다.

```text
POST /underwriting/predict
{ "age": 58, "bmi": 31.2, "claim_count_3y": 4, "smoker": true, ... }

→ { "decline_probability": 0.87 }
```

여기서 심사자가 묻는다. **"왜 0.87인데요?"**

모델은 답을 안 해준다. XGBoost 같은 트리 앙상블은 수백 개의 트리가 각자 조금씩 점수를 더한 결과라서, 코드를 뜯어봐도 사람이 읽을 수 있는 규칙이 안 나온다. 이게 흔히 말하는 블랙박스 문제다.

SHAP은 여기에 답을 준다.

```json
{
  "decline_probability": 0.87,
  "base_value": 0.12,
  "contributions": {
    "claim_count_3y": +0.41,
    "bmi": +0.18,
    "smoker": +0.11,
    "age": +0.07,
    "income_level": -0.02
  }
}
```

"평균적인 고객이면 0.12인데, 3년 청구 4건이 0.41을 올렸고, BMI가 0.18을 더 올렸다." 이제 심사자에게 설명할 수 있다.

## 2. 한 줄 정의

**SHAP은 하나의 예측값을, 각 피처(feature)가 얼마나 기여했는지로 분해하는 방법이다.**

SHapley Additive exPlanations의 약자다. Shapley는 사람 이름(Lloyd Shapley, 노벨경제학상), Additive는 "더해서 맞아떨어진다"는 뜻이다.

## 3. 익숙한 비유: 분산 트레이싱

API 응답이 500ms 걸렸다. 어디서 걸린 건가?

분산 트레이싱을 붙이면 이렇게 나온다.

```text
총 500ms
├─ Auth 체크        20ms
├─ DB 조회         310ms
├─ 외부 API 호출   150ms
└─ 직렬화           20ms
```

각 구간의 합이 전체와 정확히 맞는다. 그래서 "DB가 범인"이라고 말할 수 있다.

SHAP이 하는 일이 정확히 이거다. 예측값이라는 총량을 피처별 구간으로 쪼갠다.

```text
예측 0.87
= 기준값 0.12
+ claim_count_3y  +0.41
+ bmi             +0.18
+ smoker          +0.11
+ age             +0.07
+ income_level    -0.02
```

**기준값 + 기여도 총합 = 예측값.** 이 등식이 항상 성립하는 게 SHAP의 핵심 성질이고, "Additive"가 붙은 이유다.

## 4. 그래서 기여도는 어떻게 정하나

여기가 유일하게 조금 낯선 부분이다.

"이 피처가 예측을 얼마나 올렸나"를 재는 순진한 방법은 **그 피처를 빼보는 것**이다.

- 전체 피처로 예측: 0.87
- `claim_count_3y`만 빼고 예측: 0.46
- 차이 0.41이 이 피처의 기여도

문제는 피처끼리 상호작용한다는 거다. 순서에 따라 답이 달라진다.

- 아무것도 없는 상태에서 `claim_count_3y`를 추가 → 0.30 상승
- `bmi`, `smoker`가 이미 있는 상태에서 `claim_count_3y`를 추가 → 0.41 상승

어느 쪽이 진짜 기여도인가?

**샤플리 값의 답: 가능한 모든 추가 순서를 다 해보고 평균낸다.**. 결국 **가중 평균**이다.-

## 5. 계산량 문제와 TreeSHAP

예시는 피처가 몇개 되지 않아 계산에 문제가 없지만 실제 모델은 만들때는 많은 피처가 사용된다. 피처를 20개일 때만 계산해도 $2^{20}$ = 약 100만 번. 50개면 사실상 불가능하다.

그래서 실무에서는 근사·최적화 알고리즘을 쓴다.

| 알고리즘 | 대상 | 특징 |
| --- | --- | --- |
| **TreeSHAP** | 트리 계열 (XGBoost, LightGBM, RandomForest) | 트리 구조를 이용해 **정확한 값**을 다항 시간에 계산. 압도적으로 빠름 |
| **KernelSHAP** | 아무 모델이나 | 모델 무관하게 동작하지만 샘플링 기반 근사, 느림 |
| **DeepSHAP** | 신경망 | 역전파 활용 |

XGBoost를 쓴다면 TreeSHAP이 있어서 성능 걱정을 거의 안 해도 된다. 이게 실무에서 SHAP이 폭넓게 쓰이는 이유이기도 하다.

## 6. 함정 4가지

### 1. 인과관계가 아니다

SHAP은 "이 피처를 바꾸면 결과가 바뀐다"가 아니라 "**이 모델이** 이 피처를 이렇게 썼다"를 말한다. 모델이 편향돼 있으면 SHAP은 그 편향을 충실하게 설명해줄 뿐이다. 설명 가능성 ≠ 정당성.

### 2. 상관 피처는 기여도를 나눠 갖는다

`나이`와 `가입연수`가 강하게 상관돼 있으면 실제 영향력이 둘로 쪼개져 각각 작아 보인다. 파생 피처를 마구 넣은 모델에서 특히 헷갈린다.

### 3. 로그 오즈 / 확률 공간 혼동

6절의 주의 사항. 기여도 합을 확률처럼 화면에 노출하는 실수가 잦다.

### 4. 실시간 API에서의 비용

TreeSHAP이 빠르긴 해도 `predict`보다는 확실히 무겁다. 트래픽이 있는 엔드포인트라면 응답 시간을 반드시 측정하고 들어가야 한다.

## 7. 서비스에 붙일 때 고려사항

**설명은 예측과 분리하는 게 낫다**
`POST /predict`는 빠르게 유지하고, 설명은 `GET /predict/{id}/explanation`으로 분리하거나 비동기로 계산한다. 심사자가 "왜?"를 누르는 순간에만 필요한 경우가 대부분이다.

**설명 결과는 저장한다**
모델을 재학습하면 같은 입력에 대한 설명이 바뀐다. 나중에 "그때 왜 이렇게 판정했나"를 감사(audit)해야 할 수 있으므로, 판정 시점의 `model_version` + 입력 + SHAP 결과를 함께 남긴다. 재현이 아니라 기록으로 남기는 게 안전하다.

**Explainer는 프로세스 시작 시 한 번만 만든다**
`TreeExplainer(model)` 생성 비용을 요청마다 치르면 안 된다. 모델 로딩과 같은 라이프사이클로 관리한다.

**배치가 훨씬 싸다**
야간 배치로 전 건 SHAP을 미리 계산해두는 구조가 가능하면 그게 제일 편하다.

**노출 정책은 별도 문제다**
내부 심사자에게는 전체 기여도를, 고객에게는 상위 N개만 자연어로 변환해서 보여주는 식으로 층을 나누는 게 보통이다. 특히 금융·보험 도메인에서는 자동화된 판정 결과에 대한 설명 요구가 제도적으로 논의되는 영역이라, 어디까지 어떻게 노출할지는 개발 이전에 도메인·컴플라이언스와 합의하고 시작하는 편이 낫다.

## 8. 요약

- SHAP은 **하나의 예측값을 피처별 기여도로 쪼개는** 방법이다
- **기준값 + 기여도 합 = 예측값**이 정확히 성립한다 (분산 트레이싱의 span과 같은 구조)
- 기여도는 "모든 피처 추가 순서에 대한 평균 기여분"으로 정의된다 (샤플리 값)
- 트리 모델이면 TreeSHAP으로 정확하고 빠르게 계산된다
- 개별 설명(왜 이 고객이)과 전역 설명(모델이 뭘 보나) 둘 다 나온다
- 인과관계가 아니라 **모델의 판단 근거**를 설명하는 것뿐이다
- 서비스에 붙일 때는 예측과 분리하고, 결과를 저장하고, Explainer를 재사용한다
