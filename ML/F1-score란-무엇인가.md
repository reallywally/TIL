# F1 score란 무엇인가

## 0. 한 줄 요약

**F1 = precision과 recall을 하나로 합친 점수. 둘 중 하나라도 나쁘면 F1도 나쁘게 나오도록 설계된 숫자.**

이 한 줄을 이해하려면 precision과 recall을 먼저 알아야 하고, 그 둘이 왜 필요한지는 accuracy가 왜 못 쓰는지를 봐야 안다. 그 순서로 간다.

## 1. 왜 정확도(accuracy)로는 부족한가

사기 거래 탐지 모델을 만든다고 하자. 거래 10,000건 중 실제 사기는 100건(1%)이다.

여기서 **아무 학습도 안 하고 "전부 정상입니다"라고만 답하는 한 줄짜리 모델**을 만들어보자.

```python
def predict(transaction):
    return "정상"
```

이 모델의 정확도는 **99%**다. 10,000건 중 9,900건을 맞혔으니 틀린 계산이 아니다. 그리고 사기는 **한 건도 못 잡는다.** 완전히 쓸모없는 모델이 99점을 받는다.

실제로 학습시킨 제대로 된 모델의 정확도를 재보면 이렇다.

| 모델 | 정확도 | 사기 100건 중 잡은 것 |
| --- | --- | --- |
| "전부 정상" (쓸모없음) | **99.00%** | 0건 |
| 학습된 모델 A | **99.31%** | 78건 |
| 학습된 모델 B | **96.66%** | 97건 |

세 모델의 실제 가치는 완전히 다른데 정확도는 96~99% 사이에 뭉쳐 있다. 심지어 **사기를 97건이나 잡아낸 모델 B의 정확도가 아무것도 안 하는 모델보다 낮다.** 사기를 잡으려고 무리하게 의심한 대가로 정상 거래 331건을 오탐했기 때문이다.

정확도가 무너지는 이유는 명확하다. **정확도는 다수 클래스에 지배된다.** 99%가 정상인 데이터에서는 "정상을 잘 맞히는 능력"이 점수의 99%를 차지하고, 정작 우리가 알고 싶은 "사기를 잡는 능력"은 1%밖에 반영되지 않는다.

이런 상황을 **클래스 불균형(class imbalance)**이라고 하고, 실무의 중요한 분류 문제는 대부분 불균형하다. 사기 탐지, 이상 감지, 장애 예측, 불량품 검출, 이탈 예측, 질병 진단 — 찾으려는 것이 드물기 때문에 찾을 가치가 있는 것이다.

> **그래서 정확도 하나만 보고하는 분류 모델 보고서는 신뢰하지 않는 게 맞다.** 클래스 비율을 먼저 물어봐야 한다.

## 2. 혼동 행렬 — 틀림을 두 종류로 나눈다

정확도의 문제는 "맞음/틀림" 두 칸으로만 세는 것이다. **틀림을 두 종류로 나누면** 상황이 보인다.

앞의 모델 A(사기 78건 적발)의 결과를 4칸에 나눠 담아보자.

| | **모델: 사기라고 함** | **모델: 정상이라고 함** |
| --- | --- | --- |
| **실제 사기** | TP = 78 (제대로 잡음) | FN = 22 **놓침** |
| **실제 정상** | FP = 47  **오탐** | TN = 9,853 (제대로 통과) |

이걸 **혼동 행렬(confusion matrix)** 이라고 한다. 용어는 이렇게 읽으면 헷갈리지 않는다.

- 두 번째 글자 = **모델이 뭐라고 했나** (P = Positive/사기라고 함, N = Negative/정상이라고 함)
- 첫 번째 글자 = **그게 맞았나** (T = True/맞음, F = False/틀림)

즉 **FP = "사기라고 했는데(P) 틀렸다(F)" = 오탐**, **FN = "정상이라고 했는데(N) 틀렸다(F)" = 놓침**이다.

### 백엔드 관점: 이건 온콜 알람과 똑같은 구조다

FP와 FN의 성격 차이는 모니터링 알람을 운영해봤으면 몸으로 아는 것이다.

- **FP(오탐) = 아무 일 없는데 울리는 알람.** 임계값을 너무 낮게 잡았을 때 생긴다. 쌓이면 팀이 알람을 무시하게 된다(alert fatigue). 여기서는 정상 고객 47명의 결제가 막힌 것이다 — CS 문의가 들어온다.
- **FN(놓침) = 장애가 났는데 안 울리는 알람.** 임계값을 너무 높게 잡았을 때 생긴다. 여기서는 사기 22건이 그대로 통과한 것이다 — 금전 손실이다.

그리고 알람 임계값을 조절할 때 겪는 그 딜레마가 여기서도 똑같이 반복된다. **한쪽을 줄이면 다른 쪽이 늘어난다.**

## 3. Precision과 Recall

혼동 행렬의 네 칸에서 두 개의 비율을 뽑는다. 정의는 짧은데 어느 쪽이 어느 쪽인지 헷갈리기로 유명하다.

### Precision (정밀도) — "잡은 것 중에 진짜가 몇 %냐"

```text
Precision = TP / (TP + FP) = 모델이 사기라고 한 것 중 진짜 사기 비율
          = 78 / (78 + 47) = 78 / 125 = 0.62
```

**분모가 "모델이 사기라고 한 전체"**다. 모델의 주장을 기준으로 센다.

62%라는 건, 이 모델이 결제를 막은 125건 중 78건은 정말 사기였고 47건은 무고한 고객이었다는 뜻이다. **정밀도는 오탐과 직결된다.** 정밀도가 낮으면 CS 팀이 고생한다.

### Recall (재현율) — "진짜 중에 몇 %를 잡았냐"

```text
Recall = TP / (TP + FN) = 실제 사기 중 모델이 잡아낸 비율
       = 78 / (78 + 22) = 78 / 100 = 0.78
```

**분모가 "실제 사기 전체"**다. 정답을 기준으로 센다.

78%라는 건, 실제 발생한 사기 100건 중 78건을 막고 22건은 통과시켰다는 뜻이다. **재현율은 놓침과 직결된다.** 재현율이 낮으면 손실이 난다.

### 외우는 법

| | 기준(분모) | 낮으면 생기는 일 | 한 문장 |
| --- | --- | --- | --- |
| **Precision** | 모델이 잡은 것 | 오탐 폭증 (FP) | "부르면 대체로 맞나?" |
| **Recall** | 실제로 있는 것 | 놓침 폭증 (FN) | "있는 걸 대체로 다 찾나?" |

앞의 "전부 정상" 모델을 여기에 넣어보면 지표가 왜 필요한지 바로 보인다. TP가 0이므로 **recall = 0%**다. 정확도 99%가 recall 0%로 정직하게 드러난다.

## 4. 둘은 서로 반대로 움직인다 — 임계값

여기서 가장 실무적인 개념이 나온다. **precision과 recall은 하나의 모델 안에서도 조절할 수 있다.**

분류 모델은 사실 "사기다/아니다"를 출력하지 않는다. **확률을 출력한다.** 0.83, 0.41, 0.07 같은 값이다. 이걸 사기로 판정할지 말지는 **임계값(threshold)을 어디에 두느냐**로 결정된다.

```python
score = model.predict_proba(transaction)   # 0.0 ~ 1.0
if score >= THRESHOLD:                     # ← 이 숫자는 우리가 정한다
    block_transaction()
```

앞의 그 모델, 하나의 동일한 모델에서 임계값만 바꿔가며 재본 결과다.

| 임계값 | TP(잡음) | FP(오탐) | FN(놓침) | Precision | Recall | **F1** | 정확도 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.3 | 100 | 1,109 | 0 | 0.08 | **1.00** | **0.15** | 0.8891 |
| 0.4 | 97 | 331 | 3 | 0.23 | 0.97 | **0.37** | 0.9666 |
| 0.5 | 88 | 92 | 12 | 0.49 | 0.88 | **0.63** | 0.9896 |
| **0.6** | 78 | 47 | 22 | 0.62 | 0.78 | **0.69** ← 최고 | 0.9931 |
| 0.7 | 59 | 31 | 41 | 0.66 | 0.59 | **0.62** | 0.9928 |
| 0.8 | 36 | 20 | 64 | 0.64 | 0.36 | **0.46** | 0.9916 |

표를 위아래로 읽어보면 구조가 보인다.

- **임계값을 낮추면** 의심을 많이 한다 → recall↑ (다 잡는다) / precision↓ (오탐 폭증)
- **임계값을 높이면** 확실할 때만 잡는다 → precision↑ / recall↓ (많이 놓친다)

맨 위 줄이 극단적인 예다. 임계값 0.3에서 **recall 100%**를 달성했다. 사기를 하나도 놓치지 않았다. 그런데 정상 거래 1,109건을 같이 막았다. 서비스가 마비된다.

> **백엔드 개발자에게 중요한 사실: 임계값은 재학습 없이 바꿀 수 있는 설정값이다.**
>
> 모델 파일은 그대로 두고 `THRESHOLD` 상수만 바꾸면 precision/recall 균형이 즉시 이동한다. 커넥션 풀 크기나 rate limit을 조정하는 것과 성격이 같다. 그래서 이 값을 코드에 하드코딩하지 말고 **설정으로 빼두는 것이 실질적으로 중요하다.** 사업 상황에 따라(오탐 CS가 폭증했다, 사기 손실이 커졌다) 운영 중에 조절해야 할 값이기 때문이다.

## 5. F1 Score

### 5.1 문제 상황

이제 표에서 모델을 하나 골라야 한다. precision과 recall 두 숫자를 동시에 비교하려니 판단이 어렵다.

- 임계값 0.5: precision 0.49, recall 0.88
- 임계값 0.7: precision 0.66, recall 0.59

어느 쪽이 나은가? **두 숫자를 하나로 합친 지표가 필요하다.** 그게 F1이다.

### 5.2 그냥 평균을 내면 안 되는 이유

가장 먼저 떠오르는 건 산술평균이다. `(precision + recall) / 2`. 그런데 이건 **속일 수 있다.**

임계값을 극단으로 내려서 "전부 사기 의심"이라고 답하는 모델을 생각해보자. recall은 1.00이다(하나도 안 놓쳤으니까). precision은 0.01이다(거의 다 오탐).

```
산술평균 = (0.01 + 1.00) / 2 = 0.505   ← 50점? 절반은 쓸만하다는 뜻?
```

쓸모없는 모델이 50점을 받는다. 반대 극단도 같다. 초확실한 1건만 잡는 모델은 precision 1.00, recall 0.02 → 산술평균 0.51이다.

**산술평균은 한쪽을 극단으로 밀어서 점수를 벌 수 있다.** 우리가 원하는 건 그 반대다. **한쪽이 망가지면 점수도 망가져야 한다.**

### 5.3 조화평균

F1은 산술평균 대신 **조화평균(harmonic mean)**을 쓴다.

```
F1 = 2 × (Precision × Recall) / (Precision + Recall)
```

같은 값들을 넣어보면 차이가 명확하다.

| Precision | Recall | 산술평균 | **F1 (조화평균)** |
| --- | --- | --- | --- |
| 0.01 | 1.00 | 0.505 | **0.020** |
| 1.00 | 0.02 | 0.510 | **0.039** |
| 0.62 | 0.78 | 0.700 | **0.693** |
| 0.90 | 0.90 | 0.900 | **0.900** |

**조화평균은 작은 쪽에 끌려간다.** 한쪽이 0.01이면 다른 쪽이 1.00이어도 결과는 0.02다. 반면 두 값이 비슷하면 산술평균과 거의 같아진다(0.62/0.78 → 0.693 vs 0.700).

이게 F1의 설계 의도 전부다. **"둘 다 괜찮아야 점수를 준다."** 극단으로 밀어서 점수를 벌 수 없다.

> 왜 하필 조화평균인가: 조화평균은 비율(rate)의 평균을 낼 때 쓰는 것이고, precision과 recall은 분모가 다른 비율이다. 백엔드에서 익숙한 예로, 왕복 평균 속도를 낼 때 산술평균이 아니라 조화평균을 쓰는 것과 같은 이유다. 이유를 몰라도 실무에는 지장 없다. **"작은 쪽에 끌려간다"만 알면 충분하다.**
