# Oracle RAC는 이중화일까? — 인스턴스와 데이터베이스의 차이부터

## 들어가며

회사에서 이중화 작업 도중 Oracle RAC라는 말을 들었다. DB 이중화는 개념만 알고 있었지 실제로 해보거나 관련 단어를 들어본 적은 없어서 잘 이해가 안되었다. 정확히 RAC가 무엇인지, 그리고 평소 JPA로 붙던 "DB"와 무슨 관계인지 정리해봤다.

## 결론부터 말하면

**RAC는 서버(인스턴스) 이중화이지, 데이터 이중화는 아니다.** 이걸 이해하려면 먼저 Oracle이 "인스턴스"와 "데이터베이스"를 왜 구분하는지 알아야 한다.

## 인스턴스 vs 데이터베이스

우리는 보통 "DB에 붙는다"고 뭉뚱그려 말하지만, Oracle은 이걸 두 개로 나눈다.

| 용어 | 실체 | 비유 |
| --- | --- | --- |
| **Database** | 디스크 위의 파일들 (데이터 파일, 컨트롤 파일, 리두 로그) | 창고에 쌓인 장부 |
| **Instance** | 그 파일을 열어 SQL을 처리하는 메모리(SGA) + 백그라운드 프로세스 | 장부를 꺼내 읽고 쓰는 직원 |

파일은 혼자서 아무것도 못 한다. 서버에서 `startup`을 치면 인스턴스가 뜨고, 그 인스턴스가 파일을 열어서 비로소 쿼리를 받을 수 있게 된다.

MySQL/PostgreSQL로 치면 `mysqld` 프로세스가 인스턴스, `/var/lib/mysql` 디렉터리가 데이터베이스인 셈이다.

## 그럼 JPA는 어디에 붙는 걸까?

게시판 애플리케이션을 예로 들면 접속 흐름은 이렇다.

```text
[JPA / JDBC] → (리스너) → [Oracle 인스턴스] → [데이터 파일]
```

- JPA가 붙는 대상은 **인스턴스**다.
- 인스턴스는 DB 앞에 따로 얹힌 프록시 같은 계층이 아니라, 우리가 평소 "DB 서버"라고 부르던 그것 자체다.
- 인스턴스 없이 파일에 직접 붙는 방법은 애초에 없다.

단일 서버에서는 인스턴스 1개 = 파일 1벌이라 둘을 구분할 이유가 없다. 그래서 그냥 "DB"라고 불러도 아무 문제가 없었던 것.

## RAC: 인스턴스는 여러 개, 파일은 하나

RAC(Real Application Clusters)는 이 구분이 비로소 의미를 갖는 구성이다.

```text
[JPA] → SCAN → [인스턴스 A (서버1)] ─┐
               [인스턴스 B (서버2)] ─┴→ [데이터 파일 (공유 스토리지, 1벌)]
```

- 데이터 파일은 공유 스토리지(SAN/ASM)에 **한 벌만** 있다.
- 그 파일을 여는 인스턴스가 **서버마다 하나씩** 뜬다.
- 클라이언트는 개별 서버 IP 대신 **SCAN**이라는 하나의 이름으로 접속하고, 리스너가 여유 있는 인스턴스로 배분한다.
- 서버1이 죽으면 서버2의 인스턴스가 같은 파일을 계속 서비스한다. → 서비스가 안 끊긴다.

### 구성 요소 한 줄 정리

- **공유 스토리지**: 데이터 파일이 놓이는 곳. 모든 노드가 같은 파일을 본다.
- **인터커넥트**: 노드 간 전용 네트워크. 한 노드 메모리에 있는 블록을 다른 노드가 필요로 하면 디스크를 거치지 않고 직접 넘긴다(Cache Fusion).
- **Clusterware(Grid Infrastructure)**: 노드 상태 감시, 장애 감지, 페일오버 담당.
- **SCAN**: 클라이언트가 접속하는 단일 진입점.

## 그래서 RAC는 이중화인가?

**"무엇을" 복제하느냐에 따라 답이 다르다.**

### RAC가 이중화하는 것

- 서버, 인스턴스, 메모리, 리스너 — 즉 **처리 계층**
- Active-Active 구성이라 두 노드가 동시에 서비스한다.

### RAC가 이중화하지 않는 것

- **데이터 자체**. 파일은 한 벌이다.
- 스토리지가 통째로 죽거나, 누가 실수로 `DROP TABLE`을 하면 모든 노드가 똑같이 영향을 받는다.
- 이 관점에서 스토리지는 단일 장애점(SPOF)이다.

### 데이터 이중화는 다른 계층에서

- **ASM 미러링 / RAID**: 디스크 장애 대응
- **Data Guard**: 별도 사이트에 복제본을 두는 재해복구(DR). Active-Standby 구성.
- **백업**: 논리 오류 대응

실무에서는 보통 이렇게 조합한다고 한다.

> RAC(서버 장애) + ASM 미러링(디스크 장애) + Data Guard(사이트 재해·논리 오류)

## 주의점

- 인터커넥트로 블록을 주고받는 비용이 있어서, 같은 블록을 여러 노드가 동시에 자주 수정하는 워크로드에서는 오히려 느려질 수 있다.
- 라이선스 비용이 상당히 높다. 그래서 무중단이 중요한 금융권에서 2~4노드 정도로 많이 쓴다.
